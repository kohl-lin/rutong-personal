# 委婉职场沟通 Playbook

## 核心结构

敏感职场沟通通常包含四类信息：

1. **背景或认可**：说明为什么现在需要沟通，或在确有必要时认可具体贡献。
2. **客观事实**：描述结果、差距、限制或依赖，不评价个人态度和能力。
3. **明确动作**：说清谁需要在什么时候完成什么，或需要对方做出什么决定、提供什么支持。
4. **闭环路径**：说明下一个检查点、可提供的支持，或负责人不匹配时的转交方式。

这不是固定模板。信息较短时可以省略没有实际价值的部分，但不能省略真正的 action。

## 1. 催进度或结果未达预期

避免：

> 为什么没有达标？请解释一下。

推荐逻辑：

> 当前结果与既定目标仍有一定差距。方便的话，请在【时间】前同步主要原因、当前卡点、下一步动作及预计恢复时间，我们再一起确认是否需要额外支持。

规则：

- 描述结果与约定目标之间的差距，不给个人或团队贴负面标签。
- `支持` 不能替代责任，仍需保留明确的回复内容、下一步和时间。
- 原因未经确认时，用提问获取信息，不自行推断。

## 2. 负责人不确定

避免：

> 这个是你负责的吧？麻烦尽快处理。

推荐逻辑：

> 想确认一下，【事项】目前是由你负责跟进吗？背景是【中性原因】。如果是，麻烦在【时间】前协助完成【具体动作】；如果不是，也请帮忙指一下对应负责人，谢谢。

规则：

- 先确认 ownership，再分配责任。
- 提供转交路径，但不能让事项因负责人不明确而失去下一检查点。

## 3. 分配任务与设定 Deadline

避免：

> 大家别忘了交作业，本周必须交。

推荐逻辑：

> 请在【日期和时间】前提交【具体产物】。内容需覆盖【范围或验收要求】，后续将用于【已确认用途】。如有卡点，请在【更早的检查时间】前提出，以便在截止时间前处理。

规则：

- 写清交付物和验收范围，不只描述活动本身。
- 使用具体时间，不用“有空”“尽快”替代已经确定的 deadline。
- 可以解释产物的真实用途，但不要为了显得合理而虚构用途。

## 4. 请求跨团队或管理者支持

避免：

> 麻烦帮忙推动一下这个需求。

推荐结构：

> **需要支持：**【具体决定或介入动作】
>
> **背景与影响：**【为什么重要，使用已确认信息】
>
> **当前卡点：**【已经做过什么，目前被什么阻塞】
>
> **具体诉求：**【需要确认的优先级、资源、负责人或决定】
>
> **下一检查点：**【负责人和时间】

规则：

- 不使用模糊的“帮忙看看”，说清需要对方确认、决定或推动什么。
- 保持专业和平等，不堆叠“冒昧”“烦请”“拜托”等谦辞。
- 区分普通信息确认和正式 escalation，避免无必要地升级压力。

## 5. 通知限制、故障或强制动作

避免：

> 大家使用太多，系统不能用了。下周必须更新。

推荐逻辑：

> 当前服务容量比原计划更早达到上限，自【时间】起可能出现【可观察影响】。我们会通过【已确认恢复路径】恢复服务。为确保变更后可以继续使用，请在【截止时间】前完成【必要动作】。

规则：

- 解释机制和影响，不责怪使用者。
- 准确说明当前状态；如果上限已经达到，不写成“接近上限”。
- 清楚说明必要动作、截止时间、受影响状态和恢复路径。
- 发送前核对相对日期；未知版本或恢复时间保留占位符。

## 6. 引导对方改变行为

避免：

> 不要再用高成本方案了，太浪费。

推荐逻辑：

> 先确认对方希望达成的目标，再说明共同面对的资源或成本约束，并给出可执行的场景分配：将高成本方案保留给确实能改善结果的复杂任务，常规执行和早期草稿优先使用轻量方案。先提出一个容易尝试的调整，不要求一次性改变所有习惯。

规则：

- 不否定对方的偏好、专业判断或使用需求。
- 用结果、容量、时间或成本解释 tradeoff，不把使用选择道德化。
- 给出可用的替代路径，不只提出禁止要求。

## 7. 纠正性反馈

避免：

> 你总是犯同样的低级错误。

推荐逻辑：

> 在【时间范围或次数】内，【具体可观察问题】在【场景】中出现，并带来了【影响】。下一轮请在【里程碑】前增加【具体检查或行为】，我们在【检查时间】一起确认结果。

规则：

- 讨论可观察行为和影响，不评价性格或动机。
- 使用足够证据说明问题，避免“总是”“从不”等夸大表达。
- 写清期待的行为以及后续如何检查。

## 8. 向熟悉的同事请教

探索性沟通优先使用具体、真实不确定的问题：

> 现在每次最多可以处理【数量】对吗？如果我需要更大的结果，能不能分几次处理后再合并？这样会不会触发限流？

不要把尚未验证的想法写成正式方案或已支持能力。使用“能不能”“比如”“我在考虑”等词保留探索性。

## 常见替换

| 容易引发压力的表达 | 更清晰的表达 |
|---|---|
| 你们没达标 | 当前结果与既定目标仍有差距 |
| 解释一下为什么没做 | 请同步主要原因、卡点和下一步 |
| 这个是你负责的吧 | 想确认一下目前是由你负责跟进吗 |
| 帮忙看看 | 请协助确认 / 决定 / 完成【具体事项】 |
| 尽快处理 | 请在【明确时间】前完成【动作】 |
| 大家使用太多 | 实际需求高于原计划容量 |
| 强制更新 | 请在【时间】前完成更新，以确保变更后可以继续使用 |
| 不好意思又来打扰 | 在【检查点】前跟进一下【事项】 |

## 可复用内容的脱敏检查

将案例保存到可复用 skill 或对外分享前，删除或泛化：

- 员工、管理者、团队、客户和供应商名称；
- 内部产品、项目、模型、数据集和系统名称；
- 公司特定缩写、组织架构和角色称谓；
- 内部 URL、ID、邮箱、群组和文件路径；
- 未公开的真实指标、预算、事故、日期和承诺；
- 会暴露权限控制、系统限制或内部 escalation 路径的流程细节。

只保留解释沟通方法所必需的抽象结构。

## 最终检查

- 是否删除了对人的负面判断，但保留了客观问题？
- 对方是否一眼知道自己需要做什么、何时完成？
- 背景是否解释了要求，同时没有稀释责任？
- 提供的支持、转交方式或恢复路径是否真实明确？
- 语气是否平等自然，没有卑微、官腔或假夸奖？
- 可复用案例中是否已移除敏感信息？
